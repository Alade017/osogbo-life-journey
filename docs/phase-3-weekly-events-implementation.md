## Completed behavior

The existing three event IDs, weekdays and hours are retained. Town Market Day uses fictional Town Market; Riverlight Community Gathering and Open Courtyard Arts use fictional Youth Arts Centre. A server catalog now materializes immutable current/next Lagos-week occurrences, with absolute start/end timestamps and snapshotted venue, map references and copy. Unique keys and deterministic insertion order make repeated reads idempotent. Existing occurrences and attendance are not rewritten after catalog edits.

`get_city_events()` returns the shared schedule, server time, weather/venue availability and the current character's joined status. The three existing consumers share an account/character-scoped validated query. `WorldEnvironment` uses the server event links and occurrence transitions while retaining lighting, weather and outage behavior. `CityEventParticipation` restores attendance after reload, shows Lagos event times and handles pending/offline/error states. Map district and landmark details use explicit matching IDs and server end timestamps. The duplicated client schedule was removed; phone calendar reminders were retained separately.

No money, XP, mood, reputation, discount, fee or appliance effect was added. Database tests compare player stats (including reputation) and wallets before/after participation. Existing activity, travel and daily-task contracts are preserved.

## Contract and security details

The original `join_city_event(p_event text)` remains available and returns its established `joined/duplicate` response. Because a name alone cannot distinguish this week's request from next week's, the updated UI uses an additional `join_city_event_occurrence(p_occurrence_id uuid)` RPC. Both delegate to one private implementation. The occurrence-specific endpoint rejects a stale occurrence even when the same named event is active the following week. Legacy callers retain their name-based semantics; they cannot obtain occurrence pinning without switching to the new endpoint.

Joins derive authenticated identity, reject anonymous users, lock the current owned character, materialize bounded schedules, and capture the database clock again after possible waits. They validate the exact half-open event window, weather and saved location before inserting existing unique participation. Reads also capture time after possible materialization waits. Clients supply no player IDs, clocks, window definitions or effects. Private helpers cannot be called by browser roles. New tables have RLS, authenticated read grants and no browser writes.

The old attendance SELECT policy called `_my_character_id`, whose client execution grant was revoked. The new migration replaces that policy with an equivalent ownership subquery against RLS-protected characters, preserving isolation without exposing the helper. Actual authenticated-role reads/writes are tested locally.
