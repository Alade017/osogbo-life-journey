# Phase 3.3 daily check-in streak

Date: 2026-10-25, Africa/Lagos. The owner approved `phase-3-login-streak-plan.md`. This slice implements the registered, playable-character daily check-in only. Living costs (3.4), later gameplay and renderer adoption remain deferred.

## Behavior

A visible, online game session reads its server check-in snapshot, then explicitly checks in for the returned Lagos date if needed. Restored sessions qualify without signing out and in. Reads alone never grant XP. The first day counts as 1; consecutive Lagos days add one; a missed day makes the next check-in 1. There is no backfill, multiplier or milestone payout.

Each account/day grants **5 XP by default, at most 5 XP**, with no money. Combined with the approved daily tasks, these two features can supply at most 20 XP/day. Existing `_grant_xp` level-up effects and lifetime-mission recalculation are retained. Account claims and streak state survive character recreation, preventing another same-day grant to the new character.

The game-shell provider shares read/status state with a compact Missions summary. Pending, hidden/offline and unavailable states do not block gameplay. A confirmed newly-awarded receipt can show one reward notification; cached/repeated check-ins do not. A lost response is recovered from the stored receipt. Hidden/offline mutations are not queued. Focus/reconnect/retry reads fresh server state before another attempt. Ordinary polling cannot create an unbounded failed-mutation loop. A stale date refreshes before a still-visible/online session can attempt the new day.

## Persistence and security

New migration: `supabase/migrations/20261025152947_login_streak_check_in.sql`, generated by the installed CLI. It creates a bounded server-owned reward setting, account-keyed streak state and unique `(user_id,lagos_date)` receipts. Character deletion sets the receipt character reference null; it does not erase account/day eligibility history.

`get_login_streak()` derives account/current character and returns server date/time, reset, effective streak, reward and today's status. `check_in_login(p_date date)` accepts only the snapshot date. It verifies registered identity, obtains the per-account lock and owned-character row lock, captures the clock after waits, and rejects stale dates. For an unclaimed day, receipt/state writes, `_grant_xp` and mission recalculation are one transaction. Failures roll back all changes. Same-day retries return stored streak/reward data with `newlyAwarded=false`.

Clients cannot supply owner IDs, streak counts, rewards or trusted clocks. RLS exposes only own state/receipts; direct browser writes are revoked. Ownership policies use `auth.uid()` directly, without exposing private helper execution. RPCs have safe fixed search paths, qualified references, registered-account checks and narrow grants. A reward constraint caps configuration at 5 XP. No auth flow, starting-money grant, wallet RPC or needs rule changed.

An existing `any` cast in the touched game layout's presence heartbeat was replaced by its declared `touch_player_presence()` type (migration 0048 returns void). That call's payload, timing and behavior are unchanged. This makes the touched layout pass scoped lint without suppressing the rule.
